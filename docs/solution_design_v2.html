Solution design v2: the six-layer AML semantic layer

What each layer is, who owns it, what it holds today, and how a question travels through it
Working draft, 2026-11-10  |  Readers: AML and financial-crime practitioners, and the engineers who would maintain the solution  |  Scope: one typology technique, T0039 Circular Transactions
Status: draft, not reviewed by a domain expert. Layers 2 to 6 are our own reading of the typology text: the AML vocabulary, what each indicator needs, which data source holds each term, which table provides which source, and the rules that check the indicators. The transaction data and the customer profiles are synthetic. No accuracy measurement has been made; the model runs reported here are small trials.

1. What this version is

The first solution design described the pipeline and four knowledge layers. This version organises the knowledge as six layers, each with one kind of content and one owner, and treats layers 2 to 5 as the semantic layer: the part that defines what the data means in AML terms and how each term reaches a column. Layer 1 supplies external domain knowledge; layer 6 consumes the semantic layer, validates the evidence it returns and produces the verdicts. The files were reorganised to match, and every file path is named in one place (src/paths.py).

The semantic layer in one sentence. A question put in AML terms (“what does indicator IND02191 need, for these transfers?”) is answered from the database without anyone writing SQL: layer 3 says what is needed, layer 2 gives the terms, layer 4 says which of our data terms answer them, and layer 5 says which columns hold them. Ontop turns that chain into SQL.

2. The use case in brief

An investigator has a handful of transfers and asks a question an investigator can act on: does what I see fit a known typology technique, indicator by indicator, and what can the available data not tell me? The answer has to use the typology’s own words, say plainly where the data stops, and be produced without customer data leaving the institution. The solution is not a suspicion score, a SAR decision or a search for suspicious transfers: the investigator supplies the transfer ids.

  1. The investigator describes the case and gives the transfer ids.
  2. The system identifies the typology technique from the published typology (layer 1), or asks, or offers up to three candidates.
  3. It retrieves what each indicator of that technique needs for the named transfers (layers 3, 2, 4, 5), and only that.
  4. It checks the pattern on what came back and reports each indicator as: structure matches, does not hold (with the failed rule), facts only, or cannot check here (layer 6). A gap is named by the typology data source that would hold the data.
  5. It shows account background as context and summarises in plain words, checked against the verdicts.

Worked example. The investigator gives transfers 2131053, 2204314 and 2282865 and describes money going round in a circle. The system selects T0039, retrieves 12 rows in about two seconds, and reports: IND02191 structure matches (the funds go round in time order and return to the first account; the business-rationale part is not checked); IND02195 facts only (3 hops, 3 of them between banks; the typology gives no threshold, and cross-border is not in the data); and the other seven cannot check here, each naming the data source that would hold what is missing, for example IND02193 needs Contractual and Invoice Data, Customs and Border Records and Trade Documentation.

4.4 Layer 4: data semantic and alignment

PurposeExplains how our data concepts relate to the AML concepts. It has two parts: the vocabulary of our tables, and the alignment that says which AML term each data term is a kind of.
OwnerThe data owner. Both parts change when the database changes; the AML terms they point up to do not.

4.6 Layer 6: validation and execution

PurposeValidates the evidence that came back through layers 2 to 5, evaluates the indicator rules and produces verdicts that can be audited: each verdict says which rule failed, or which data is missing and where it would be.
OwnerAML knowledge for the rules, engineering for the execution.
HoldsSHACL shapes (9 rule checks, each tagged as close to the typology text, our reading, or added by this project). A registry of 9 indicators with what each indicator’s rules do not check. The code that builds the candidate loop from the returned rows and turns the SHACL result into a verdict.
Filesvalidation/shapes/t0039.shapes.ttl, validation/shapes/t0039.skeletons.ttl (the seven indicators without rules, not run), validation/indicator_registry.json; code in src/loop_check.py, src/indicators.py
VerdictsStructure matches the description; does not hold (with the failed rule ids); facts only (IND02195: the typology gives no number for “multiple hops”); cannot check here (with the missing terms and the sources that would hold them). The state comes from the declarations and the SHACL result, never from the model.
Not yetA separate rules module in code; evidence and provenance kept as a durable audit record (today the rule tags are in the files and each run’s SPARQL, SQL, rows and rules are shown on the page, but nothing is stored as a signed or versioned record).

4.7 The OBDA engine

Ontop 5.5.0 with DuckDB sits under layers 2 to 5. For one question it is given one mapping (the transfers, the profiles and the typology CSV files merged) and one ontology (layers 1 to 4 merged), and it does two things: rewrites a query by the ontology (an AML term becomes the data term under it) and unfolds it by the mapping into SQL. It must be given the ontology: without it, a query in AML terms returns no rows and no error, so a guard rejects any query that names a term the model should not use, and “cannot check” is decided from the declarations, never from an empty result.

5. How one question travels through the layers

Figure 2. The pipeline on the left; the knowledge each step reads on the right, with the files. The model appears three times: intent, queries, summary.
#StepWhat happensLayersFiles
1Intent analysis (Qwen)Chooses a technique from a catalogue read through Ontop, or asks, or offers candidates. Code checks the id exists and sits under the stated tactic.1src/intent.py
2Intent SPARQL (Qwen)Writes two small queries naming only the technique and the transfer ids. A guard rejects any data term the model names itself.1, 3src/prompt.py, src/sparql_guard.py
3Rewrite (Ontop)The query asks for what the technique’s indicators need (layer 3); Ontop replaces each AML term (layer 2) by the data term under it (layer 4).2, 3, 4src/unified.py
4Unfold (Ontop)The data terms become table and column references and then SQL; DuckDB runs it, read-only. For the example: 12 rows, about 15,000 characters of SQL.5src/ontop_run.py
5Source reasoningAsks which data sources the technique lists, which terms each holds and which are covered; code reads the same chain and compares.1, 3, 4, 5src/typology.py, src/sources.py
6Candidate loopPivots the long-format rows to one row per transfer, orders by time, builds the candidate loop graph.6src/pivot.py, src/pipeline.py
7SHACL and verdictsRuns the rules, gives each of the nine indicators a state, and names each gap by the data source that would hold it.6 (3, 1)src/loop_check.py, src/indicators.py
8Summary (Qwen)Writes a short summary; code checks verdict words, places, numbers and business-rationale claims, with a template as fallback.6src/summarize.py

Who decides what. The model chooses a technique (checked against layer 1), writes queries that name no data term, and writes the summary (checked). Everything that depends on the data model or on the typology is decided by the layers: what an indicator needs (3), which columns hold it (4, 5), whether the pattern holds and what the verdict is (6). The model sees the question, the public typology catalogue and a nine-term vocabulary; transaction rows go only to Ontop, DuckDB, SHACL and code. The one exception is the summary step, which reads a short fact sheet with transfer ids, account ids, verdict states and the synthetic background; it can be switched off or fed pseudonymised ids, but as built it is not.

8. Verified, not done, and questions

Verified (engineering checks)

  • Queries through Ontop return the same rows as hand-written SQL on all 26 gold cases; SHACL agrees with the gold verdicts on all 19 loop cases. The suite has 144 tests, including checks on the layer layout.
  • What Ontop returns for the data sources, terms and tables equals what code reads from the files and declarations.
  • The demo page gives the same result for the worked example in Gold mode and in intent mode with the real model, before and after the files were split into layers and moved.

Not done

  • No comparison between “the model writes SQL directly” and this pipeline, and no test across model sizes. The design is four conditions, gold SQL compared on returned id sets, “silently wrong” as the primary outcome, and Wilson intervals.
  • No evaluation of intent accuracy at scale; candidate suggestions are known to be unstable.
  • No expert review of layers 2 to 6 or of the gold cases. No technique other than T0039.

Questions for AML reviewers

  1. Is our reading of what each indicator needs, and of which data source holds which term, sensible?
  2. Which concepts belong in the AML core ontology beyond the eighteen (Party, Company, …), and should Transaction be distinct from FundsTransfer?
  3. Is time ordering a defensible addition to the loop rule? Should a two-account round trip count as circular?
  4. Is there a conventional threshold for “multiple hops” (IND02195)?
  5. For which indicators is the absence of country a hard blocker, and for which could a proxy such as bank be acceptable?
  6. For a second technique, Money Mule Exploitation: how should fast in-and-out movement, “similar amounts” and account age be defined? The synthetic profiles have no account-opening date.
