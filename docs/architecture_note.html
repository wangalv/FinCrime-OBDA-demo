Constraining a small local model with OBDA

An AML-typology demo: architecture, knowledge layers, and what is and is not established
Working note, 2026-11-10  |  Intended readers: AML and financial-crime practitioners with some technical background  |  Scope of this note: the “intent” mode of the demo, applied to one typology technique (T0039, Circular Transactions)
Status: draft, not reviewed by a domain expert. The mapping from each indicator to the data it needs, the rules that check the indicators, the AML vocabulary used to bridge typology and data, and the statements of which data source holds which term and which table provides which source, are our own reading of the typology text. The gold cases used for regression were generated by us and frozen by the project owner without expert review. No accuracy measurement has been made yet; the only model runs reported here are small trial runs. The transaction data and the customer profiles are synthetic.

1. Purpose

An investigator receives an alert and asks a question about a few transfers. We want the system to answer by checking the indicators of an AML typology technique one by one, to say plainly which indicators the available data can and cannot speak to, and never to let a language model decide what the data says.

The project tests one hypothesis: if a small local model only expresses the investigator’s intent, and everything that depends on the data model and on the typology is handled by deterministic components (an ontology-based data access engine, a validation language, and ordinary code), the system is more reliable than asking the same model to write SQL directly. Results will be reported as counts with confidence intervals, not as a guarantee of accuracy. Section 2 gives the argument for why OBDA matters here. This note describes the architecture only; it does not report that comparison, which has not been run (section 10).

2. Why OBDA: moving correctness out of the model

Thesis. In a conventional text-to-SQL setup, the quality of the answer is bounded by the quality of the model. The model has to know the schema, the join paths, what a typology indicator means in terms of columns, and then write valid SQL. Reliability becomes a property of the model, which pushes institutions toward the largest models, usually hosted outside the institution. Ontology-based data access (OBDA) moves that knowledge out of the model and into declarations that people write, review and version. The claim we want to test is that, with this split, the reliability of the answer depends much less on how capable the model is, so a small model running inside the institution is enough. This is a hypothesis; section 10 says what has and has not been tested.

Four consequences

  1. Capability is decoupled from correctness (hypothesis). In an early informal attempt, the same local model asked to write the SQL for IND02191 directly succeeded in one of four tries, repeating the same alias error. That is four attempts and not a measurement. Under OBDA the model’s remaining tasks are selection and transcription. The test that would support the claim is to run the same questions across models of different sizes and across conditions, and to see whether the rate of “silently wrong” answers varies less between models under OBDA than under direct SQL. This has not been run.
  2. The errors that remain are visible and bounded. The model writes no SQL, so it cannot invent a column or a join. Invented vocabulary is rejected by a guard (Ontop would otherwise return an empty result without complaint). A wrong technique is named in the answer and must come from the typology catalogue. A weak model is therefore more likely to fail by asking again, by picking a different technique or by being rejected than by returning plausible but wrong numbers. What remains is a valid but wrong technique choice, and a summary that is not fully faithful (the check on it is imperfect).
  3. Expertise goes where practitioners can review it. The Alignment, the bridge and the rules are short, declarative and readable without SQL. If a practitioner disagrees about what IND02191 needs, one line changes; no prompt is re-tuned and no model is replaced. The same ontology works with any model, and with a different database by replacing the mapping only.
  4. Local deployment in sensitive settings. The model is a 9-billion-parameter model served on one machine (Ollama), and nothing leaves the institution. More specifically, in the query path the model sees only the question, the public typology catalogue and a nine-term intent vocabulary; transaction rows go to Ontop, DuckDB, SHACL and code, all local and deterministic. A direct text-to-SQL approach usually puts the schema, and sometimes sample rows, in the prompt, so a weaker local model costs accuracy there and a stronger one tempts the user to send data out. One precise limit: the summary step receives a short fact sheet that includes the transfer ids, the account ids, the verdict states and the (synthetic) customer background. It can be switched off, since a template summary exists, or fed pseudonymised ids; as built, it is not.

What this argument does not claim

  • It does not remove the model; it moves the weight. Intent analysis still needs a model that is capable enough, and our trials show its candidate suggestions are fragile (section 9).
  • The cost moves to knowledge engineering. A mapping, an Alignment, a bridge and rules have to be written for each technique and each data source. We have done this for one technique.
  • Deterministic does not mean right. All the declarations here are our draft reading. A wrong Alignment gives the same wrong answer every time, whichever model is used. The gain is that such errors are reproducible and reviewable, not that they are absent.

What would count against the thesis

If direct SQL generation by the same small model, given the same schema and the same output checks, performs as well as the OBDA pipeline; or if the OBDA pipeline’s error rate changes with model size as much as direct SQL does.

3. Scope and data

  • Scenario. An investigator names transfers by id and asks whether they look like a given pattern. The system identifies the typology technique, checks every indicator of that technique that the data can support, and reports the rest as “cannot check here”.
  • Technique covered. T0039 Circular Transactions (tactic: Layering), which has nine indicators in the typology. Other techniques are recognised by the intent step but reported as outside what this demo can check.
  • Transactions. A table of 5,078,345 transfers derived from the IBM synthetic AML transaction set. It has account ids, bank flag (same or different bank), timestamp at minute resolution, a log-scaled amount, and a laundering label. It has no country or location field, so cross-border cannot be checked. A currency is not a country, and a different bank is not a different jurisdiction.
  • Customer profiles. 515,080 rows (customer type, industry, tenure in days, PEP flag, risk rating). These are synthetic, generated by us, not part of the IBM data. Tenure is a random integer with no start date, so it cannot be compared with transaction time. Profiles are shown as account background only and are never evidence for any indicator.
  • Technology. Ontop 5.5.0 (OBDA engine), DuckDB, pyshacl, a local Qwen 3.5 9B model served by Ollama, and a Streamlit page.

4. Architecture

Figure 1 shows the pipeline (left) and the declared knowledge each step reads (right), organised in four layers by who changes them: the typology publisher, an AML practitioner, or whoever changes the database. The model appears three times: it chooses a technique, writes two small queries, and writes the final summary. Everything between those is deterministic.

Figure 1. The intent-mode pipeline and the four layers of knowledge Ontop reads. The model never sees the data model, never writes SQL, and never decides a verdict.

5. Knowledge layers

Each layer states one kind of knowledge once, and is grouped by who changes it. A new typology release changes layer 1; an AML practitioner who disagrees about what an indicator needs changes layer 2; a change of database changes layers 3 and 4 and leaves layers 1 and 2 alone.

How a requirement becomes a column

Typology indicator IND02191: “cyclical patterns in funds or asset transfers that ultimately revert to the same origin across multiple accounts…”
Alignment IND02191 needsTerm FundsTransfer, originator, beneficiary, transferTime
Source originator, beneficiary, transferTime are recorded in DS0019 Transaction Logs, one of the eight sources the typology lists for T0039; the transaction table realises DS0019
Bridge fromAccount is a sub-property of originator; toAccount of beneficiary; timestamp of transferTime
Mapping fromAccount ← column from_account; timestamp ← column ts (of the transaction table)

If the chain stops before a column, as it does for jurisdiction or invoice, the indicator is reported as one the data cannot answer. This is a property of the declarations, not a runtime guess, and a missing term returns no rows rather than an error.

A source is “available” when every term recorded in it has a data term under it, “partly” when some do, and “background only” when no AML term is answered from it but a table provides it (the synthetic profiles, shown only as account context). Transaction Logs counts as partly because the raw amount is recorded there and the data holds only a logarithm of it. Three consistency checks run over the declarations: every term an indicator needs is recorded in a source the typology lists for the technique; every source named exists in the typology; every AML term that has a data term under it is recorded in a source that some table provides.

7. Worked example

Question: “Look at transfers 2131053, 2204314 and 2282865.” These three transfers are one of the 19 loop cases in our gold set. Technique: T0039.

  1. Evidence query. The query asks, for T0039, every indicator, every term it needs, and the value of that term for each named transfer. Ontop answers in about two seconds with 12 rows, all for two indicators: IND02191 (originator, beneficiary and transfer time, for each of the three transfers: 9 rows) and IND02195 (same-institution flag: 3 rows). The other seven indicators contribute no rows: the terms they need have no data under them. This is silent by design; the “cannot check” status comes from the declarations, not from the empty result.
  2. Generated SQL. The SQL Ontop produced for this query is about 15,000 characters long and contains 39 UNION branches over the transaction table. It is machine-generated and not meant to be read; what matters is that the same query written with data terms returns identical rows.
  3. Candidate loop. The three transfers are ordered by time (2131053 → 2204314 → 2282865) and form a loop that returns to the originating account.
  4. Verdicts.
IndicatorStateDetail
IND02191Structure matchesAll rules held. Not checked: “lacking a legitimate business rationale” (only a warning if a record claims one).
IND02195Facts only3 hops, 3 legs between banks. No verdict: the typology gives no number for “multiple hops”. Not checked: cross-border, high-risk or offshore jurisdictions, frequency, lack of business justification.
IND02192, 02193, 02194, 02196, 02197, 02198, 02199Cannot check hereEach lists the missing terms and the data sources that would hold them. For example IND02193 needs Invoice and Shipment, which would be in Contractual and Invoice Data, Customs and Border Records and Trade Documentation; IND02196 needs the declared business activity (Business Activity and Operations) and the raw amount (Transaction Logs).

The account background shows, for the three accounts involved: customer type Individual, tenure 2,903, 429 and 2,299 days, PEP flag no, risk rating Low for all three (synthetic profiles, shown as context only).

What this example shows: the system reports a pattern match for one indicator, a set of facts for another, and an explicit “cannot check” for the remaining seven, in one pass. What it does not show: that the model selects the right technique reliably, or that any of the verdicts would be endorsed by an investigator.

9. Where the model does and does not help

  • Intent analysis. The model chooses from a long catalogue. In a hand-made trial of 12 phrasings, loop-like questions mapped to the right technique, other common methods mapped to different techniques, and vague or unrelated questions produced a clarifying question. That sample is small and the phrasings were ours. Sub-techniques are chosen unreliably when the user gives only a name.
  • Candidate suggestions are fragile. When the user says only that transfers are related, the model proposes up to three techniques. Because it cannot see the transactions, the candidates change with rewording and across runs. An example in the prompt was copied verbatim into the answers until it was replaced by placeholders. A more reliable design would have Ontop fetch the transfers first and have code describe their shape (connected end to end, similar amounts, same bank) before listing candidates; this is not built.
  • Query writing is now close to transcription. In intent mode the two queries are almost fixed templates in which only the technique and the ids change. The decisions about what to fetch moved into the Alignment and Ontop. This is deliberate, but it means intent mode does not test whether a small model can write SPARQL; the earlier modes (the model writes queries in AML terms or in data terms) are kept for that comparison.
  • Summary. The model writes it and code checks it, but the check does not guarantee that every sentence is faithful. The model reads a short fact sheet (transfer ids, account ids, verdict states, synthetic customer background), so this is the one step in which it sees case data.

10. What has been verified, and what has not

Verified (engineering checks)

  • Ontop returns the same rows as hand-written SQL on all 19 loop cases and all 7 account-background cases.
  • A query written with AML terms returns the same rows as the same query written with data terms; without the ontology it silently returns zero rows (the guard exists for this reason).
  • Variable predicates bound by the Alignment, typology and transactions in one virtual graph, and unanswerable terms producing no rows rather than errors, were all tested directly before being built in.
  • SHACL agrees with the gold verdict on all 19 loop cases (after the gold was aligned to SHACL, which is the authority for the rules; the change is recorded). The test suite has 132 tests.
  • The data source layer: the sources, terms and tables that Ontop returns are the same as the ones read in code from the typology files and the declarations, and three consistency checks over the declarations pass (section 5). That shows the declarations agree with each other and with the typology; it does not show that they are right.
  • In four real runs of the intent mode, both model-written queries passed the guard each time, returned 12 long-format rows, and produced verdicts matching the gold. This is a trial, not a measurement.

Not done

  • No comparison between “the model writes SQL directly” and the OBDA pipeline. The planned design has four conditions, hand-written gold SQL compared on returned transfer-id sets, a primary outcome of “silently wrong” (executes, passes all checks, differs from gold), a pilot of 5 runs per cell, a full run of 20 per cell, and Wilson intervals.
  • No evaluation of intent accuracy at scale.
  • No test of the thesis in section 2: the same questions run with models of different sizes, under both direct SQL and the OBDA pipeline.
  • No expert review of the Alignment, the bridge, the rules or the gold cases.
  • No technique other than T0039 is connected.

11. Limitations and questions for AML reviewers

These are the points where practitioner judgment would change the system most.

  1. Needs per indicator. The typology links data sources to the technique, not to each indicator. Is our Alignment (for example, IND02195 needs transfers, a same-institution flag and a jurisdiction) a reasonable reading?
  2. Data sources. The typology links data sources to a technique only. Is our reading of which AML terms each source holds, and of which table provides which source, sensible? Two choices to look at: Transaction Logs counts as only partly available because the raw amount is recorded there and the data holds just a logarithm; the synthetic customer profiles count as “background only” for KYC records.
  3. Loop definition. Is time ordering a defensible addition? The data contains time-ordered loops of 2 to 10 legs, so we do not search for fixed-length loops. Should a two-account round trip count as circular? Under our reading it does.
  4. “Multiple hops” (IND02195). The typology gives no threshold, so the system reports hops and between-bank legs and refuses a verdict. Is there a conventional threshold an investigator would expect?
  5. Cross-border and jurisdiction. The data has no country. For which indicators is this a hard blocker and for which could a proxy (bank, currency) be acceptable?
  6. A second technique. Money Mule Exploitation (T0011) is the candidate. Of its nine indicators we judge two answerable and two partly answerable. Fast in-and-out movement needs a definition of the window and of “similar amounts”; newly opened accounts need an account-opening date that the synthetic profiles do not have; related accounts is not in the data. We have not chosen definitions and will not do so without a practitioner.
  7. Synthetic data. The transactions are from a synthetic generator with a laundering label, and the profiles are ours. Nothing in this note says how the approach would behave on real alerts.

The system’s output is a structured reading of the evidence against the indicator text. It is not a suspicion score, a SAR decision, or a statement that laundering occurred.
