Solution design: typology-driven transfer review with OBDA

Use case, architecture, knowledge modules and maintenance model
Working draft, 2026-11-10  |  Readers: AML and financial-crime practitioners, and the engineers who would maintain the solution  |  Scope: one typology technique, T0039 Circular Transactions
Status: draft, not reviewed by a domain expert. What each indicator needs, which data source holds each AML term, which table provides which source, the rules that check the indicators, and the AML vocabulary are our own reading of the typology text. The transaction data and the customer profiles are synthetic. No accuracy measurement has been made; the model runs reported here are small trials.

1. Use case

1.1 The situation

An investigator has an alert, or a suspicion, about a handful of transfers. The question is not “is this laundering?” but a narrower one an investigator can act on: does what I see fit a known typology technique, indicator by indicator, and what can the available data not tell me? The answer has to be in the typology’s own words, has to say plainly where the data stops, and has to be produced without customer data leaving the institution.

1.2 Actors

ActorRole
InvestigatorDescribes what they see, gives the transfer ids, reads the answer, and can open the evidence behind it.
AML practitioner (knowledge owner)Reviews and maintains what each indicator needs, which data source holds each term, and the rules that check the indicators.
Data engineer (data owner)Maintains the mapping of the database to the data vocabulary, and the alignment from it to the AML vocabulary.

1.3 Main flow

  1. The investigator describes the case in their own words and includes the transfer ids.
  2. The system identifies the typology technique the description points to, from the published typology (302 techniques and sub-techniques). If the description is unclear it asks, or offers up to three candidates to choose from.
  3. The system retrieves what each indicator of that technique needs for the named transfers, and only that. Which data an indicator needs is declared once, in AML terms, not written into any query.
  4. The system checks the pattern on the retrieved transfers: for T0039, whether the funds leave an account, pass through other accounts in time order and return to the first one.
  5. The system reports every indicator of the technique, one of four ways: the structure matches the description; it does not hold (with the rule that failed); facts only (the typology gives no threshold); or cannot check here. A gap is named by the typology data source that would hold the missing data, for example Contractual and Invoice Data.
  6. The system shows account background (customer type, tenure, PEP flag, risk rating) as context. It is never evidence for an indicator.
  7. The system summarises in plain words, checked against the verdicts. The investigator can open the SPARQL, the SQL, the returned rows, the rules and the typology behind the answer.

1.4 Alternate flows

  • The intent is unclear. The system asks a question or offers candidate techniques. The candidates are the model’s guesses and are not stable across rewordings; the investigator chooses.
  • The technique is outside what the solution can check. The system names it and says so. Only T0039 is connected.
  • No transfer ids. The system asks for them. It does not search for candidates.
  • A transfer is not found. The system says which ids were not found and judges the others.

1.5 Worked example

The investigator writes: “The money seems to go round in a circle and come back to where it started. The ids are 2131053, 2204314, 2282865.” The system selects T0039 and returns, in about two seconds of retrieval, 12 rows for the three transfers. It then reports:

IndicatorResultDetail
IND02191Structure matchesThe funds go round in time order and return to the first account. Not checked: whether the cycle lacks a legitimate business rationale.
IND02195Facts only3 hops, 3 of them between banks. The typology gives no threshold for “multiple hops”. Cross-border and high-risk jurisdictions are not in the data.
The other sevenCannot check hereEach names the missing data and the sources that would hold it. IND02193 needs Contractual and Invoice Data, Customs and Border Records and Trade Documentation.

Account background for the three accounts: individuals, 2,903, 429 and 2,299 days open, not PEP, low risk (synthetic profiles, context only).

1.6 What the solution does not claim

  • It reads a structure against indicator text. It is not a suspicion score, a SAR decision, or a statement that laundering occurred.
  • “Structure matches the description” is not stronger than that. The business-rationale part of IND02191 is not decidable from transfer data.
  • It does not search for suspicious transfers. The investigator supplies them.

1.7 Why this design fits the use case

The use case asks for three things a free-text-to-SQL approach struggles to give together: an answer in the typology’s own terms, an honest statement of what cannot be checked, and no customer data going to an outside model. The design gets them by moving what depends on the data model and on the typology out of the language model and into declarations that people write and review. The model only works out the intent and writes the summary, tasks within reach of a small model running inside the institution. This is a hypothesis; section 5 says what has and has not been tested.

2. Solution architecture

The pipeline is on the left; the declared knowledge each step reads is on the right, in six modules. Modules 2 to 5 are the semantic layer that Ontop exposes as one virtual graph; module 1 is the published typology it is built against, and module 6 consumes and validates what comes back. The model appears three times (intent, queries, summary); everything between is deterministic.

Figure 1. Pipeline and the six knowledge modules, with the files each uses. The model never sees the data model, never writes SQL and never decides a verdict.

3.1 How a requirement becomes a column

Typology indicator IND02191: “cyclical patterns in funds or asset transfers that ultimately revert to the same origin across multiple accounts…”
Requirement IND02191 needsTerm FundsTransfer, originator, beneficiary, transferTime
Source these terms are recorded in DS0019 Transaction Logs, one of the eight sources the typology lists for T0039; table tx realises DS0019
Alignment fromAccount is a sub-property of originator; toAccount of beneficiary; timestamp of transferTime
Mapping fromAccount ← column from_account; timestamp ← column ts of table tx

If the chain stops before a column, as for jurisdiction or invoice, the indicator is reported as one the data cannot answer, and the source recorded for the missing term names the gap. This follows from the declarations, not from a runtime guess; a missing term returns no rows rather than an error.

5. Safeguards, privacy and maintenance

5.1 Safeguards in the design

  • The model writes no SQL and names no data term. The guard rejects anything outside the technique, the ids, the requirement predicates and a fixed set of structure terms.
  • An empty result is never read as “no evidence”. Ontop returns no rows for a term the data does not have, and for an AML-term query when the ontology is not supplied. “Cannot check” comes from the declarations, and the ontology is always passed to Ontop.
  • Rule provenance is explicit. Each rule is tagged as close to the typology text, our reading, or added by this project.
  • The summary is checked for verdict words, places the facts never mention, numbers not in the facts, and business-rationale claims; otherwise a template is shown. The check does not guarantee every sentence is faithful.

5.2 What the model sees

In the query path the model sees the question (with the ids), the public typology catalogue and a nine-term intent vocabulary. Transaction rows go only to Ontop, DuckDB, SHACL and code. The summary step is the exception: it reads a short fact sheet that includes the transfer ids, the account ids, the verdict states and the synthetic background. It can be switched off (a template summary exists) or fed pseudonymised ids; as built, it is not. The model runs on the same machine (Qwen 3.5 9B through Ollama), so nothing leaves the institution.

There are 14 hand-written files in all: amlo.ttl, typology_adapter.ttl, aml_core.ttl, typology_requirements.ttl, source_vocabulary.ttl, aml_data_alignment.ttl, tx_features.r2rml.ttl, customer.r2rml.ttl, tx_features.lens.json, query_vars.ttl, the shapes file, the registry file, and two Ontop connection files. Splitting the knowledge by module raised the count from 11 to 14; each file now has one kind of content and one owner. Generated files are rebuilt on demand and are not edited. Three consistency checks run over the declarations: every term an indicator needs is recorded in a source the typology lists for the technique; every source named exists in the typology; and every AML term with a data term under it is recorded in a source that some table provides.

6. Status and open questions

Verified (engineering checks)

  • Queries through Ontop return the same rows as hand-written SQL on all 26 gold cases (19 loop cases and 7 account-background cases); SHACL agrees with the gold verdicts on all 19 loop cases. The suite has 132 tests.
  • The sources, terms and tables that Ontop returns equal the ones read in code from the typology files and the declarations.
  • The demo page gives the same result for the worked example in gold mode and in intent mode with the real model, before and after the knowledge layers were reorganised.

Not done

  • No comparison between “the model writes SQL directly” and this pipeline, and no test across model sizes. The design is four conditions, gold SQL compared on returned id sets, “silently wrong” as the primary outcome, and Wilson intervals.
  • No evaluation of intent accuracy at scale; candidate suggestions are known to be unstable.
  • No expert review of the declarations, the rules or the gold cases. No technique other than T0039.

Questions for AML reviewers

  1. Is our reading of what each indicator needs, and of which data source holds which term, sensible?
  2. Is time ordering a defensible addition to the loop rule? Should a two-account round trip count as circular?
  3. Is there a conventional threshold for “multiple hops” (IND02195)?
  4. For which indicators is the absence of country a hard blocker, and for which could a proxy such as bank be acceptable?
  5. For a second technique, Money Mule Exploitation: how should fast in-and-out movement, “similar amounts” and account age be defined? The synthetic profiles have no account-opening date.
